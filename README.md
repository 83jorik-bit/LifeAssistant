# Жизненный навигатор — Android MVP

Прототип приложения из концепции «Жизненный навигатор»: карта потребностей, бюджет по категориям,
контроль подписок и личный ИИ-помощник. Все данные в этой версии — **моковые** (см.
`data/repository/MockRepository.kt`), реальных интеграций с Яндекс Картами, банками и
маркетплейсами нет — это отдельный этап (см. «Что дальше» ниже).

## Стек

- Kotlin + Jetpack Compose (Material 3)
- Архитектура: MVVM (ViewModel + StateFlow), один экран = один ViewModel
- Навигация: Navigation-Compose, нижнее меню с 4 разделами
- Данные: `MockRepository` — синглтон с тестовыми данными, имитирует сетевую задержку

## Структура проекта

```
app/src/main/java/com/lifenavigator/app/
├── MainActivity.kt                  — точка входа, Scaffold + нижняя навигация
├── data/
│   ├── model/Models.kt              — модели: PlacePoint, BudgetCategory, Subscription…
│   └── repository/MockRepository.kt — источник тестовых данных (замена на реальный API)
└── ui/
    ├── navigation/NavGraph.kt       — маршруты и пункты меню
    ├── theme/Theme.kt               — цвета/тема Material 3
    └── screens/
        ├── map/            — Карта потребностей (список точек + фильтры)
        ├── budget/          — Бюджет по категориям с прогресс-барами
        ├── subscriptions/   — Подписки: список, переключатель вкл/выкл
        └── assistant/       — Чат с ИИ-помощником (ответы по ключевым словам)
```

## Как собрать и запустить

1. Установите **Android Studio** (Koala или новее).
2. Откройте папку `LifeNavigator` как проект (File → Open).
3. Дождитесь синхронизации Gradle (подтянет зависимости автоматически — нужен интернет).
4. Запустите на эмуляторе или устройстве (Shift+F10 / кнопка Run), минимальная версия Android — 8.0 (API 26).

Если у вас нет Android Studio, можно собрать через терминал (нужен установленный Android SDK):

```bash
./gradlew assembleDebug
# APK появится в app/build/outputs/apk/debug/app-debug.apk
```
Готового `gradlew` (Gradle Wrapper) в архиве нет — при первом открытии в Android Studio она
сама предложит его сгенерировать. Либо соберите через локально установленный Gradle:
`gradle assembleDebug` (см. также автосборку через GitHub Actions ниже).

## ⚠️ Full-версия MapKit SDK нужна для реального поиска

Поиск организаций в MapKit доступен только в **full**-версии библиотеки (в `app/build.gradle.kts`
используется `com.yandex.android:maps.mobile:...-full`, а не `-lite`, как в первых версиях этого
проекта). Ключ при этом остаётся тем же самым — просто у full-версии больше возможностей
(поиск, геокодирование, маршрутизация, панорамы) и она немного тяжелее по размеру APK.

Бесплатное использование MapKit (включая full-версию) возможно при соблюдении условий Яндекса:
https://yandex.ru/dev/commercial/doc/ru/concepts/mapkit — там же уточняйте актуальные лимиты,
если планируете реальную нагрузку, а не тестирование.

**Что показывает карточка места (тап по элементу списка):**
- рейтинг Яндекса, число оценок и число отзывов — приходят сниппетом `BusinessRating1x`
  (сниппеты надо запрашивать явно через `SearchOptions.snippets`, иначе рейтинга не будет);
- адрес, расстояние, часы работы, телефон — из `BusinessObjectMetadata`;
- кнопки маршрута (на машине / транспортом / пешком) и переход в карточку организации.

## Регистрация, вход и согласие на обработку данных

### Что работает сейчас

**Вход через Яндекс ID и VK ID** — по стандартному протоколу Authorization Code + PKCE,
без SDK провайдеров. Пароль пользователь вводит на странице Яндекса или VK в браузере,
приложение его не видит и не хранит. `client_secret` не используется: в мобильном
приложении его невозможно сохранить в тайне, и PKCE придуман именно как его замена.

**Перед входом обязательно подписывается согласие** на обработку персональных данных —
с текстом и подписью пальцем. Порядок принципиальный: обрабатывать данные до получения
согласия нельзя.

### Как включить вход

1. **Яндекс ID:** зарегистрируйте приложение на oauth.yandex.ru, в адресах возврата
   укажите `lifenavigator://auth/yandex`, полученный client_id впишите в `local.properties`
   как `YANDEX_CLIENT_ID`.
2. **VK ID:** создайте приложение в кабинете id.vk.ru, адрес возврата
   `lifenavigator://auth/vk`, client_id — в `VK_CLIENT_ID`.
3. Пока значения пустые, кнопки входа показываются неактивными с подсказкой — это
   честнее, чем кнопка, которая молча не работает.

Обе интеграции написаны по документации, но **на живых ключах я их проверить не мог**.
Вероятные места, где может потребоваться правка: у VK ID обязателен `device_id`
из редиректа (он обрабатывается) и возможны отличия в составе полей ответа.

### Своего сервера регистрации нет — и вот почему

Собственная регистрация по email и паролю требует сервера: база учётных записей, хранение
паролей хешами, подтверждение почты, восстановление доступа. Развернуть его вместо вас
я не могу, но важнее другое — **выбор хостинга здесь не свободный**.

Часть 5 статьи 18 Федерального закона № 152-ФЗ (в редакции Федерального закона
от 21.07.2014 № 242-ФЗ) требует, чтобы базы данных с персональными данными граждан
Российской Федерации находились **на территории России**. Поэтому популярные бесплатные
сервисы авторизации (Firebase Authentication, Supabase, Auth0 и подобные) для такого
приложения не подходят: их серверы за пределами России. Бесплатность здесь ни при чём —
проблема в размещении данных.

Что подходит:
- **Вход через Яндекс ID / VK ID** — сделано. Учётные записи хранит сам провайдер,
  своей базы паролей у нас нет вовсе. Для начала этого действительно достаточно.
- **Свой сервер в российском облаке** (Yandex Cloud, VK Cloud, Selectel, Timeweb и т. п.)
  с любым открытым решением авторизации, которое можно развернуть самостоятельно.

### Согласие на обработку персональных данных

Текст лежит в `ConsentStore.kt` и показывается целиком перед подписью. Он составлен
с опорой на статью 9 Федерального закона № 152-ФЗ, упоминает требование о локализации
баз данных (242-ФЗ) и закон об информации № 149-ФЗ.

**Это черновик, а не готовый юридический документ.** Я не юрист, и перед публикацией
текст должен проверить специалист. Как минимум в нём не заполнены данные оператора
(наименование, ИНН, адрес) — они помечены как «УКАЗАТЬ», потому что зависят от того,
кто именно будет собирать данные: физлицо, ИП или компания.

**Про подпись пальцем.** Она фиксирует факт согласия вместе с датой и редакцией текста,
но собственноручной подписью не является и усиленной электронной подписью по
Федеральному закону № 63-ФЗ тоже. Чтобы она имела силу простой электронной подписи,
оператор должен отдельно определить правила её использования. Эта оговорка показана
пользователю в самом приложении, а не спрятана в документации.

Сейчас подпись сохраняется только на устройстве. Когда появится сервер, её нужно будет
передавать и хранить на стороне оператора — иначе доказать факт согласия будет нечем.

## Бюджет: доход, лимиты, оплата

- **Доход за месяц** вводится вручную вверху экрана. Видно, сколько дохода не распределено
  по лимитам и сколько осталось с учётом фактических трат.
- **Лимиты общие для всех месяцев**: план составляется один раз и продолжает действовать
  в следующем месяце — вводить заново не нужно.
- **Свои категории** заводятся вручную, помимо встроенных. Траты и лимиты работают с ними
  одинаково: внутри они различаются ключом (`GROCERY` против `custom:<uuid>`).
- **Оплата из приложения** — заглушка с объяснением. Для настоящих платежей нужен платёжный
  провайдер (ЮKassa, CloudPayments, СБП через банк-эквайер), договор и счёт для приёма
  средств. Экран ввода карты, который никуда не отправляет деньги, добавлять не стали.
- **Автоматическая загрузка дохода и трат из банка** не сделана по той же причине, что и
  раньше: нужен доступ к банковским API, то есть договор, согласие пользователя на обработку
  операций и требования к защите платёжных данных.

## Публикация в RuStore

Приложение подготовлено под RuStore. Что для этого сделано и что нужно от вас.

### Что уже сделано в коде

- **Нет зависимости от сервисов Google.** Это главное. Раньше геолокация бралась через
  `FusedLocationProviderClient` из Google Play Services, а на части устройств, где
  пользуются RuStore, сервисов Google нет вовсе — там такая сборка просто не определяла бы
  местоположение. Сейчас координаты даёт сам MapKit
  (`MapKitFactory.getInstance().createLocationManager()`), сторонних сервисов не требуется.
- **Релизная подпись** настроена в `app/build.gradle.kts`: параметры берутся из
  `local.properties` или переменных окружения, сам ключ в репозиторий не попадает.
- **Номер версии** задаётся снаружи (`VERSION_CODE` / `VERSION_NAME`), чтобы выпускать
  сборку без правки файлов. RuStore не принимает повторно уже опубликованный `versionCode`.
- **Сборка релиза** — workflow `.github/workflows/release-rustore.yml`, запускается вручную
  и отдаёт подписанные AAB и APK.
- **Иконка приложения** — своя адаптивная, а не системная заглушка.
- `targetSdk` = 35 (RuStore требует ≥ 28), 64-битные библиотеки MapKit включены.

### Автоматическая загрузка в RuStore

В workflow «Release for RuStore» есть галочки `publish` и `send_to_moderation`.
При включении сборка сама загружается в Консоль через публичное API RuStore
(`scripts/rustore-publish.sh`): получение JWE-токена → создание черновика версии →
загрузка AAB → при отдельном подтверждении отправка на модерацию.

Отправка на модерацию по умолчанию выключена намеренно: загрузить черновик безопасно,
а модерация — это уже публикация для пользователей, и запускать её случайным прогоном
сборки не стоит.

**Что для этого нужно.** ID аккаунта разработчика сам по себе не подходит: в документации
RuStore сказано, что параметр `companyId` для авторизации признан устаревшим и вместо него
используется `keyId`. Поэтому в Консоли нужно сгенерировать **пару ключей**
(раздел «API RuStore» во вкладке «Компания» или «Разработчик») и добавить в секреты
репозитория:

- `RUSTORE_KEY_ID` — числовой ID ключа из таблицы ключей. Именно ID, а не название:
  на этом спотыкаются чаще всего.
- `RUSTORE_PRIVATE_KEY` — приватный ключ, который показывается один раз при создании пары.

Скрипт написан по документации и по нескольким независимым реализациям (подпись строки
`keyId + timestamp` алгоритмом RSA c SHA-512), но **на живом аккаунте я его проверить
не могу**. Первый запуск лучше делать с выключенной модерацией: в худшем случае получите
понятную ошибку от API, а не публикацию.

**Что должно быть готово до первого запуска:**

1. **Приложение уже создано в RuStore Консоли** с тем же package name
   `com.lifenavigator.app`. API создаёт только новую ВЕРСИЮ существующего приложения —
   само приложение и его карточку (иконка, описание, скриншоты) оно не заводит.
2. **Секреты релизной подписи заданы.** Без них сборка выходит неподписанной, а RuStore
   такую отклоняет. Workflow теперь проверяет это заранее и останавливается с понятным
   сообщением, а скрипт дополнительно проверяет сам файл на наличие подписи.
3. **Формат сборки.** Для первой публикации выбирайте `apk`: у AAB своя процедура —
   RuStore, в отличие от Google Play, не подписывает файлы сам, поэтому перед загрузкой
   AAB в Консоли нужно отдельно настроить ключ подписи приложения. APK этого не требует.

### Что нужно сделать вам

1. **Создать релизный ключ** и сохранить его надёжно:
   ```bash
   keytool -genkeypair -v -keystore release.keystore \
     -alias lifenavigator -keyalg RSA -keysize 2048 -validity 10950
   ```
   Этот ключ нельзя терять и нельзя менять: при потере обновить приложение под тем же
   package name не получится — придётся публиковать заново, потеряв установки и отзывы.
   Debug-ключ из папки `keystore/` для публикации не годится: он лежит в репозитории
   открыто, то есть подписать им может кто угодно.
2. **Добавить секреты репозитория** (Settings → Secrets and variables → Actions):
   `RELEASE_KEYSTORE_BASE64`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`,
   `RELEASE_KEY_PASSWORD` (плюс уже добавленные `MAPKIT_API_KEY` и `RASP_API_KEY`).
3. **Запустить workflow** «Release for RuStore», указав версию, и скачать артефакты.
4. **Зарегистрироваться в RuStore Консоли**, создать приложение и загрузить AAB или APK.
5. **Подготовить для карточки**: иконка 512×512, скриншоты, описание, возрастной рейтинг.
6. **Опубликовать политику конфиденциальности.** Она обязательна: приложение запрашивает
   геолокацию и передаёт запросы в сервисы Яндекса. В политике нужно честно указать, какие
   данные собираются и зачем.

### О чём стоит подумать отдельно

- **Лицензии Яндекса.** MapKit и API Расписаний используются по их условиям, в том числе
  с обязательным указанием источника данных (в приложении такая подпись уже есть).
  Перед коммерческой публикацией стоит перечитать их условия использования: бесплатные
  лимиты и правила для публичных приложений отличаются от условий для тестов.
- **Обновления через RuStore SDK.** У RuStore есть SDK для обновления приложения изнутри.
  Он не обязателен и пока не подключён: это отдельная зависимость из их репозитория,
  и добавлять её имеет смысл, когда появится живая аудитория.
- **R8/минификация** для релиза намеренно выключена. MapKit активно использует нативный код,
  и включать сжатие без проверки на реальном устройстве рискованно: собраться соберётся,
  а падать начнёт уже у пользователей.

## Обновление без удаления приложения

Раньше новую сборку приходилось ставить только после удаления старой — Android ругался на
несовпадение подписи. Причина: Gradle подписывал debug-сборки локальным ключом
`~/.android/debug.keystore`, а он на вашем компьютере и на раннере GitHub Actions разный.

Теперь в репозитории лежит общий ключ `keystore/lifenavigator-debug.keystore`, и он прописан
в `app/build.gradle.kts`. Все сборки — и локальные, и из Actions — подписываются одинаково,
поэтому APK просто накатывается поверх установленного, данные и иконка сохраняются.

Поставить обновление можно как обычно (открыть APK на телефоне) или командой:

```bash
adb install -r app-debug.apk
```

**Про безопасность:** это ключ только для debug-сборок, и он намеренно лежит в репозитории
в открытом виде — иначе его не получилось бы использовать и локально, и в CI. Для публикации
в Google Play нужен отдельный release-ключ, который в репозиторий класть нельзя: его хранят
в секретах и никому не показывают.

## Маршруты из карточки места

- **Машина / Транспорт / Пешком** — открывают Яндекс Карты (параметр `rtt=auto|mt|pd`
  из официальной документации URL-схемы).
- **Самокат** — передаётся `rtt=sc`. ⚠️ Это значение в документации Яндекса **не описано**,
  оно подобрано по аналогии и не проверено. Если приложение откроет маршрут не в режиме
  самоката — код другой (при нераспознанном `rtt` Яндекс берёт режим из прошлой сессии).
- **Такси** — отдельная официальная ссылка Яндекс Go
  (`https://3.redirect.appmetrica.yandex.com/route?...`). Если Go не установлен, ссылка ведёт
  на его страницу в магазине приложений.

## Бюджет

Экран бюджета работает по-настоящему, без тестовых данных:

- **Лимиты по категориям** задаются вручную и сохраняются между запусками
  (`BudgetStorage`, SharedPreferences + JSON).
- **Траты** добавляются вручную: сумма, категория, комментарий. Каждую можно удалить.
- **Разбивка по месяцам**: траты группируются по месяцу, можно листать назад.
  Вперёд не листаем — планировать будущие месяцы экран пока не умеет.
- **Сводка**: потрачено, лимит, остаток (или перерасход) и сколько можно тратить в день,
  чтобы уложиться до конца месяца.
- Категории без лимита и без трат не показываются, чтобы список не превращался в простыню.

**Чего здесь нет:** автоматической подгрузки трат из банка. В исходной концепции это было,
но для этого нужен доступ к банковским API — то есть договор с банком или агрегатором,
согласие пользователя на обработку операций и, скорее всего, прохождение требований
по защите платёжных данных. Пока этого нет, траты вводятся руками, и это честнее,
чем показывать цифры, взятые из воздуха.

## Категории, фильтры и сортировка

- Категории: аптеки, продукты, клиники, красота, пункты выдачи, кафе и рестораны,
  одежда и обувь, образование, транспорт. Их можно **комбинировать** — чипы работают
  независимо, «Все» сбрасывает фильтр.
- Сортировка: сначала по удалённости с шагом 0,1 км, внутри одного шага — по оценке
  от высокой к низкой.
- Подписи меток на карте тёмно-оранжевые и пропадают при отдалении (порог
  `LABELS_MIN_ZOOM` в `MapScreen.kt`). Настоящей жирности у подписей в MapKit нет —
  плотность достигается размером и широкой белой обводкой.

**Транспорт:** категория ищет наземные остановки, трамвайные, метро, железнодорожные
станции и платформы электричек, автовокзалы, речные вокзалы и причалы (по ним запрашиваются
не только организации, но и топонимы). Для остановок в карточке остаются только маршруты
пешком и на самокате, а кнопка внизу называется «Маршруты».

Чтобы открывалась именно карточка остановки с проходящими маршрутами, а не организация с
отзывами, используется **собственный URI объекта** из `UriObjectMetadata` (вида `ymapsbm1://…`).
Обрабатывает ли приложение Яндекс Карт эту схему, в документации не описано, поэтому в
`YandexMapsLauncher.openPlaceCard` выстроена цепочка запасных вариантов: URI объекта → карточка
организации по `oid` → поиск по названию → веб-версия. Сами линии транспорта внутри приложения
**не рисуются** — это отдельная задача.

## Карта, метки и подписи

- Метки — значки категорий: белый кружок с эмодзи категории внутри (рисуется в
  `categoryMarkerBitmap`, отдельных векторных иконок под каждую категорию нет).
- По метке можно тапнуть — откроется та же карточка места, что и из списка
  (идентификатор места лежит в `userData` метки).
- Подписи появляются только начиная с 18-го зума (`LABELS_MIN_ZOOM`), до этого
  на карте только значки.
- У каждой категории свой цвет (`NeedCategory.colorArgb`), и он применяется
  единообразно: кайма значка на карте, подпись метки и надпись категории в фильтре.
- Чужой слой точек интереса скрыт (`HIDE_POI_STYLE`), подложка не тронута.

## Меню, вход и настройки

Компактная шапка вместо полноразмерного `TopAppBar` — он занимал заметную часть
экрана впустую. В шапке кнопка меню с двумя пунктами:

- **Войти** — честная заглушка. Настоящая аутентификация требует сервера (хранение
  учётных записей, выдача токенов) либо входа через готового провайдера вроде Яндекс ID.
  Нерабочей формы логина здесь нет намеренно.
- **Настройки** — радиус поиска (1/3/5 км). Настройка настоящая: сохраняется между
  запусками и сразу применяется к поиску.

## Данные между запусками

Моковых мест в списке больше нет. Последний результат поиска сохраняется
(`PlacesCache`, SharedPreferences + JSON) и показывается при следующем запуске,
пока не обновится геолокация. При самом первом запуске список пуст — до первого поиска.

## Транспорт: расписание из API Яндекс Расписаний

Кнопка «Расписание и маршруты» в карточке остановки открывает расписание **внутри приложения**
(`RaspRepository` + `ScheduleSheet`). Как это работает:

1. `nearest_stations` — ищем станцию рядом с координатами места (радиус 2 км).
2. Сопоставляем найденную станцию с названием места. Это не формальность: если брать просто
   ближайшую, для остановки автобуса у дома можно подсунуть железнодорожную платформу
   в квартале отсюда и показать расписание электричек как расписание этой остановки.
   Берём станцию либо с совпадающим названием, либо совсем рядом (до 300 м).
3. `schedule` — ближайшие рейсы на сегодня, уже ушедшие отсекаются.
4. Ссылка на полное расписание берётся из `type_choices` в ответе — там же покупка билетов.

**Городские остановки открываются прямо в Яндекс Картах — сразу на расписании.** Если у
остановки есть `stopId` (его вытаскиваем из URI, который отдаёт MapKit), строится ссылка
`?masstransit[stopId]=…&mode=stop` — она открывает карточку остановки на прибытии транспорта,
а не на описании с отзывами. Именно этого не хватало: переход по `oid` или обычному поиску
приводил на обзор организации. Формат ссылки в официальной документации URL-схемы не описан,
он взят из того, как устроены ссылки самой веб-версии Карт, поэтому в
`YandexMapsLauncher.openPlaceCard` за ним идёт цепочка запасных вариантов.

Логика кнопки «Расписание и маршруты»: есть `stopId` (городская остановка) → сразу уходим
в Яндекс Карты; нет `stopId` (вокзал, станция) → показываем расписание внутри приложения
по данным Яндекс Расписаний.

**Значки транспорта различаются по виду** (`TransportKind`): автобусная остановка — 🚌,
ж/д станция и вокзал — 🚂, метро — красная «М», причал и речной вокзал — ⛴. Вид определяется
по названию и рубрике из Яндекса; порядок проверок важен, потому что «станция метро» содержит
и «станци», и «метро».

**Куда ведёт кнопка расписания:**
- городская остановка и метро → сразу Яндекс Карты. В Яндекс Расписаниях городского
  транспорта нет, и попытка запросить его заканчивалась бесполезным «рейсов больше нет»;
- вокзал, ж/д станция, причал → расписание внутри приложения по данным Яндекс Расписаний.

**Чего добиться не удалось:** гарантированно открывать Яндекс Карты сразу на вкладке
«Расписание». Для этого нужна ссылка с `masstransit[stopId]`, а идентификатор остановки
MapKit не отдаёт: для остановок-топонимов он возвращает непрозрачный URI вида
`ymapsbm1://geo?data=…`, где этого идентификатора просто нет. Остаётся попытка с
недокументированным `mode=stop`; если приложение её проигнорирует, откроется карточка
на обзоре — как и раньше.

**Важное ограничение самого сервиса:** Яндекс Расписания знают только **междугородний**
транспорт — электрички, поезда, автобусы дальнего следования, паромы, самолёты. Городских
автобусов, трамваев и их остановок там нет, об этом прямо сказано в документации Яндекса
(за городским транспортом он отсылает обратно к API Карт). Поэтому для обычной остановки
у дома приложение честно пишет, что расписания нет, и предлагает открыть её в Яндекс Картах —
выдумывать данные в этом случае нечем.

**Лицензионное требование:** использование API обязывает указывать Яндекс Расписания как
источник данных, поэтому подпись внизу шторки расписания — не украшение, а условие лицензии.
Убирать её нельзя.

Ключ хранится как `RASP_API_KEY` в `local.properties` (локально) и в секретах репозитория
(для сборки в GitHub Actions) — так же, как ключ MapKit. В репозиторий он не попадает.

**Ограничения текущей реализации поиска** (`YandexSearchRepository.kt`):
- На карте скрыт чужой слой точек интереса (`HIDE_POI_STYLE` в `MapScreen.kt`) — подписаны
  только наши места из списка. Подложка (дороги, дома, улицы) не тронута. Чтобы убрать
  что-то ещё, в стиль добавляется нужный тег из документации MapKit «Стили карты».
- На каждую категорию идёт **несколько** поисковых запросов («продукты», «супермаркет»,
  «магазин у дома» и т. д.), результаты объединяются и чистятся от дублей по идентификатору
  организации. Одна формулировка выдавала далеко не всё: сети вроде «Магнита» и маленькие
  кофейни просто не попадали в первую страницу. Размер страницы увеличен с 10 до 30.
  Побочный эффект: с ростом числа категорий и формулировок одно обновление списка — это
  уже **около 31 запроса** к поиску. На бесплатном лимите MapKit (25 000 запросов в сутки)
  это примерно 800 обновлений в день на весь проект — для личного использования запас
  большой, но при росте аудитории это первое, что упрётся в потолок.
- Область поиска передаётся как `BoundingBox`, а не `Circle`: поиск MapKit поддерживает только
  point, boundingBox, polyline и polygon, а на круг нативная библиотека падает без внятной ошибки.
- Используется `SearchManagerType.ONLINE`, потому что офлайн-карты мы нигде не скачиваем и искать
  в офлайн-кэше не в чем. В примерах документации используется `COMBINED` — если понадобится
  офлайн-режим, менять нужно в `YandexSearchRepository`.
- **Тексты отзывов и фотографии MapKit SDK не отдаёт.** В SDK есть только счётчики
  (сколько оценок и сколько отзывов) — сами тексты в составе метаданных отсутствуют.
  Поэтому за отзывами приложение отправляет пользователя в Яндекс Карты по кнопке
  (`YandexMapsLauncher.kt`), а не показывает их у себя.
- Маршрут строится не внутри приложения, а передаётся в Яндекс Карты по URL-схеме
  `yandexmaps://...&rtext=...&rtt=...`. Если приложения нет — открывается веб-версия.
  Рисовать маршрут прямо на нашей карте тоже возможно (в full-версии есть маршрутизация) —
  это отдельная задача, пока не сделана.
- «Онлайн-оплата» и «есть подписка» для реальных точек всегда `false` — это специфичные для
  концепции приложения признаки, которых нет в данных Yandex Business напрямую.
- Категории «Транспорт» и «Саморазвитие» не участвуют в реальном поиске (они больше про бюджет/
  подписки, чем про точки на карте) — как и в тестовых данных, там будет пусто.
- Поиск идёт в радиусе 3 км от пользователя, до 10 результатов на категорию.

## Настройка API-ключа Yandex MapKit (обязательно перед сборкой)

Ключ **не хранится в коде и не коммитится в git** — он читается из файла `local.properties`
в корне проекта (этот файл уже в `.gitignore`).

1. В корне проекта скопируйте `local.properties.example` в `local.properties`
2. Впишите туда свои ключи:
   ```
   MAPKIT_API_KEY=ваш-ключ-здесь
   RASP_API_KEY=ваш-ключ-расписаний
   ```
3. Пересоберите проект (Build → Rebuild Project в Android Studio)

**Важно:** если этот ключ раньше был выложен в открытом GitHub-репозитории — его стоит
**перевыпустить** в кабинете разработчика Яндекса (https://developer.tech.yandex.ru/),
старый лучше отозвать: публично засвеченный ключ может использовать кто угодно, и лимиты
запросов будут расходоваться не вами.

Как получить/перевыпустить ключ:
1. Зайдите на https://developer.tech.yandex.ru/
2. Раздел «MapKit Mobile SDK» → создать новый ключ (или отозвать старый и выпустить новый)
3. Убедитесь, что в настройках ключа разрешён `applicationId` вашего приложения:
   `com.lifenavigator.app`

## Что дальше (не реализовано в этой версии)

Каждый пункт — отдельная задача, требующая внешних ключей/договоров:

1. **Банковские API** — синхронизация транзакций (обычно через агрегаторов вроде Точка API,
   Тинькофф API или Open Banking). Требует согласия пользователя, шифрования, возможно PCI DSS.
2. **Реальный ИИ-помощник** — заменить `MockRepository.getAssistantReply()` на вызов LLM (например,
   Anthropic API) с контекстом бюджета и подписок пользователя.
3. **Бэкенд** — сейчас всё в памяти приложения. Нужен сервер (REST/GraphQL) + база данных для
   хранения профиля, истории трат, поставщиков.
4. **Оплата и маркетплейс** — интеграция с платёжным провайдером (ЮKassa, CloudPayments) и
   каталогами поставщиков.
5. **Публикация** — аккаунт разработчика Google Play, прохождение модерации, политика
   конфиденциальности (обязательна из-за работы с финансовыми данными).
6. **Реальный рейтинг мест** — возможно, доступен через отдельные поля MapKit
   (`BusinessRating1xObjectMetadata`/`BusinessRating2xObjectMetadata` встречаются в SDK), но я не стал
   их подключать без проверки на реальной сборке — стоит изучить отдельно.

## Известные ограничения прототипа

- Данные не сохраняются между запусками (нет базы данных/Room).
- Ассистент не «умный» — просто подбирает готовый ответ по ключевым словам.
- Маршрут «за один выезд» из концепции ещё не реализован (нужен Yandex Routing API).
