# LifeAssistant — журнал реализации исполнительной архитектуры

**Целевая основа:** `docs/EXECUTION_ARCHITECTURE_0.2_DRAFT.md`  
**Согласованные ограничения:** `docs/PROJECT_DECISIONS_2026-11-15.md`

Этот журнал отделяет фактически реализованные элементы от целевых компонентов, которые пока существуют только в архитектуре.

## Инкремент 1 — контракты операции и Action Registry

В ветке `architecture/execution-foundation` добавлены:

- `OperationId`, `SessionId`, `ActionId`;
- версионированный `ActionRequest` с параметрами и ключом идемпотентности;
- типизированные значения параметров;
- `OperationStatus` с состояниями жизненного цикла из архитектуры 0.2;
- `ActionExecutionResult`, в котором успешность определяется только статусом `COMPLETED`;
- неизменяемый `ActionRegistry` с проверкой неизвестных действий, версии контракта, обязательных параметров, типов и ограничений значений;
- начальный каталог 12 операций бюджета, задач, календаря и сохранённых мест, включая подтверждаемое завершение задачи;
- модульные тесты контрактов и проверки реестра.

### Принципиальные ограничения первого инкремента

1. Новые контракты пока не подключены к существующему `VoiceCommandDispatcher`. Действующая функциональность приложения не заменяется непроверенным кодом.
2. `executorKey` — логическая ссылка. Реальные Functional Executors будут подключены на этапе Execution Engine.
3. Все операции изменения в начальном каталоге требуют подтверждения. Это консервативная стартовая политика, а не окончательная матрица всех действий.
4. Для действий оставлена категория безопасности `UNCLASSIFIED`. Распределение по категориям А/Б выполняется только после отдельного согласования матрицы рисков; реестр не должен угадывать категорию.
5. Confirmation Manager, SAM и Execution Engine этим инкрементом ещё не реализованы.
6. Существующие `AssistantActionResult`, `AppDataChanges` и хранилища сохраняются до последовательной миграции.

## Инкремент 2 — единый Confirmation Manager

В той же ветке реализованы:

- `ConfirmationManager` с переходами `AWAITING_CONFIRMATION → CONFIRMED → EXECUTING → COMPLETED/FAILED`;
- привязка подтверждения, отмены и завершения одновременно к `sessionId` и конкретному `operationId`;
- запрет второй активной операции в текущей локальной сессии помощника;
- единое хранилище состояния операции на SharedPreferences с синхронной фиксацией каждого перехода;
- миграция ранее подготовленных задач, событий и бюджетных операций из двух старых SharedPreferences-наборов;
- последовательная миграция старых записей: если обнаружено несколько прежних pending-действий, они не отбрасываются и импортируются по одному;
- защита миграции от прерывания между сохранением нового состояния и удалением старой записи;
- состояние `RESULT_UNKNOWN`: если процесс прервался после начала выполнения, действие не запускается повторно автоматически;
- тесты жизненного цикла, конфликтов, идентичности сессии/операции, отмены, восстановления и миграции.

### Границы инкремента 2

1. `VoiceCommandDispatcher` теперь использует один менеджер подтверждений для задач, календаря и бюджета.
2. Существующие локальные хранилища и доменные операции сохранены. Их вызов пока выполняется через временный compatibility bridge в диспетчере; это ещё не целевой `Execution Engine`.
3. Время жизни подготовленной операции намеренно не ограничено: срок действия указан в архитектуре как открытый вопрос и не должен вводиться без отдельного решения.
4. Новая команда при активном ожидании не исполняется; помощник сообщает, что сначала нужно подтвердить или отменить подготовленное действие.
5. Категории безопасности А/Б пока не назначаются автоматически. Их распределение по конкретным операциям остаётся открытым решением.

## Инкремент 3 — SAM policy evaluator

Добавлен самостоятельный `SecurityAuthorizationManager`:

- проверяет корректность запроса по Action Registry;
- проверяет разрешение на функциональный домен;
- применяет обязательный минимум аутентификации для категорий А и Б;
- позволяет пользовательским настройкам повышать защиту, но не понижать обязательный минимум;
- требует привязку усиленной аутентификации категории А к конкретному `operationId`;
- требует явное подтверждение и отдельное ознакомление с предупреждением для категории А;
- требует подтверждение для категории Б;
- возвращает `REQUIRES_CLASSIFICATION` для неразмеченных операций изменения данных и не угадывает категорию;
- записывает решение проверки в append-only JSONL-журнал в приватном каталоге приложения;
- блокирует операцию, если событие безопасности не удалось надёжно записать.

Добавлены модульные тесты для прав доменов, категорий А/Б, повышения минимального уровня защиты, привязки усиленной аутентификации, подтверждений и отказа при недоступном аудите.

### Границы SAM

SAM пока не подключён к compatibility bridge. Это намеренно: конкретное распределение текущих операций по категориям А/Б и источник аутентификационных доказательств остаются открытыми решениями. Подключение SAM с текущими `UNCLASSIFIED` мутациями либо заблокировало бы все рабочие изменения, либо потребовало бы выдумать классификацию. Ни то ни другое недопустимо.

### Инкремент 2 — усиление Confirmation Manager

Поверх существующего менеджера подтверждений внесены следующие изменения:

- Добавлено поле `expiresAtEpochMillis` в `PendingOperation`; оно сохраняется в `SharedPreferences`.
- Если срок операции явно задан и истёк, она переводится в `EXPIRED`, сначала записывается в историю, затем удаляется из активного слота.
- Добавлен отдельный переход `reject()` в `REJECTED`; пользовательский отказ «нет» больше не смешивается с отменой «отмена».
- `VoiceCommandDispatcher` различает отказ и отмену.
- Восстановление прерванной операции теперь прекращает инициализацию с ошибкой, если не удалось прочитать состояние или надёжно записать `RESULT_UNKNOWN`. Неопределённый результат не маскируется.
- Добавлены тесты отказа, истечения срока и отказоустойчивого восстановления.

**Незакрытое архитектурное решение:** конкретная длительность срока действия подготовленной операции пока не задана в архитектуре. Поэтому новые операции пока сохраняют `expiresAtEpochMillis = null` и не истекают автоматически. Механизм истечения уже поддерживает явно заданный срок; произвольный TTL не вводится без согласования.

## Следующий инкремент

Следующий шаг — определить и согласовать матрицу категорий А/Б для зарегистрированных операций и контракт источника аутентификационных доказательств. Затем подключить SAM к Confirmation Manager и новому `Execution Engine`, чтобы все изменения данных проходили централизованную проверку безопасности перед вызовом Functional Executors.

Каждый инкремент сопровождается сборкой и проверкой до подключения следующего уровня. Рабочие функции не удаляются до появления проверенной замены.
