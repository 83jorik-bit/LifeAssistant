# LifeAssistant
## Целевая архитектура исполнительной системы

**Версия:** 0.1  
**Дата:** 14 ноября 2026 года  
**Статус:** Проект архитектуры для согласования

---

# 1. Назначение документа

Документ определяет целевую архитектуру исполнительной системы LifeAssistant.

Главная задача — создать единый механизм, через который интеллектуальный помощник сможет управлять всеми функциональными возможностями приложения.

Система должна обеспечивать:
- единый приём и обработку команд;
- понимание намерений пользователя;
- проверку допустимости операций;
- подтверждение действий, требующих согласия;
- гарантированное разграничение подготовки и выполнения операций;
- контроль фактического результата;
- согласованное изменение данных;
- синхронизацию всех зависимых интерфейсов;
- единое управление напоминаниями;
- восстановление состояния после сбоев и перезапуска.

# 2. Основные архитектурные принципы

## 2.1. Единый исполнительный механизм

Все операции изменения данных должны проходить через единую исполнительную систему.

Ни локальный ИИ, ни облачная модель, ни отдельный интерфейсный модуль не должны обходить этот механизм.

Это относится к:
- задачам;
- календарю;
- бюджету;
- расходам и доходам;
- лимитам;
- сохранённым местам;
- подпискам;
- будущим функциональным модулям.

## 2.2. Разделение интеллектуальной и исполнительной частей

ИИ отвечает за понимание естественного языка, контекста и намерений.

Исполнительная система отвечает за проверку, разрешение, выполнение и подтверждение результата.

Модель ИИ не должна самостоятельно объявлять операцию выполненной.

## 2.3. Приоритет решений пользователя

Источником актуальных требований являются последние согласованные решения в переписке проекта.

Репозиторий отражает историческое состояние реализации и служит источником технических сведений.

Если код противоречит более позднему решению пользователя, приоритет имеет решение пользователя.

## 2.4. Достоверность результата

Каждая операция должна иметь проверяемый результат.

Система не должна сообщать об успешном выполнении, если данные фактически не сохранены или действие не завершено.

# 3. Целевая архитектура

Предлагается следующая структура.

## 3.1. Assistant Controller

Центральный координатор взаимодействия пользователя с приложением.

Функции:
- принимает текстовые и голосовые команды;
- получает контекст диалога;
- определяет маршрут обработки;
- передаёт запрос интеллектуальному компоненту;
- направляет сформированное намерение в исполнительную систему;
- возвращает пользователю результат.

Controller не должен непосредственно изменять данные функциональных модулей.

## 3.2. Intelligence Layer

Интеллектуальный слой.

Включает:
- YandexGPT или другую облачную модель;
- локальный интеллектуальный движок;
- обработку естественного языка;
- контекст диалога;
- интерпретацию намерений;
- формирование структурированных запросов.

Облачная и локальная модели должны использовать единый контракт передачи намерений.

При недоступности облачной модели локальный режим сохраняет доступ к разрешённым функциям.

## 3.3. Action Registry

Реестр доступных операций.

Каждая операция имеет:
- уникальный идентификатор;
- название;
- функциональный модуль;
- тип операции;
- входные параметры;
- требования к подтверждению;
- правила проверки параметров;
- исполнитель;
- описание возможных результатов.

Новые функции приложения должны подключаться через этот механизм, а не через отдельные специальные ветви обработки голосовых команд.

## 3.4. Confirmation Manager

Единый менеджер подтверждений.

Вместо двух независимых очередей подтверждения для задач и финансов предлагается одна общая система.

Объект ожидающей операции должен содержать:

- `operationId`;
- `sessionId`;
- `actionType`;
- `parameters`;
- `createdAt`;
- `expiresAt`;
- `status`;
- `confirmationPolicy`.

Предусматриваются состояния:

- `PREPARED` — операция подготовлена;
- `AWAITING_CONFIRMATION` — ожидается согласие;
- `CONFIRMED` — подтверждена;
- `REJECTED` — отклонена;
- `EXPIRED` — срок подтверждения истёк;
- `EXECUTING` — выполняется;
- `COMPLETED` — успешно завершена;
- `FAILED` — завершилась ошибкой;
- `CANCELLED` — отменена.

Правила:

1. Подтверждение относится к конкретному `operationId`.
2. Простое «да» не может подтверждать произвольную старую операцию.
3. При появлении новой команды система проверяет, не конфликтует ли она с ожидающей операцией.
4. Изменение параметров требует повторного подтверждения.
5. Отказ пользователя отменяет соответствующую операцию.
6. Истечение срока автоматически закрывает возможность подтверждения.
7. После перезапуска приложения состояние ожидающих операций должно восстанавливаться либо безопасно завершаться.

Вопрос о допустимости нескольких одновременно ожидающих операций необходимо окончательно утвердить отдельно. Предлагаемый первоначальный вариант — одна активная операция подтверждения в рамках диалоговой сессии.

## 3.5. Execution Engine

Единый исполнительный механизм.

Получает только проверенные и разрешённые операции.

Основные этапы:

1. Проверка структуры запроса.
2. Проверка обязательных параметров.
3. Проверка прав и ограничений.
4. Проверка подтверждения.
5. Проверка актуальности операции.
6. Выполнение.
7. Проверка результата сохранения.
8. Регистрация результата.
9. Публикация события изменения данных.

Execution Engine не должен доверять утверждениям модели ИИ о выполнении действий.

## 3.6. Functional Executors

Отдельные исполнители функциональных модулей:

- Budget Executor;
- Task Executor;
- Calendar Executor;
- Map Executor;
- Subscription Executor;
- будущие исполнители.

Каждый исполнитель реализует единый контракт.

Он отвечает за выполнение операций конкретного модуля и не должен самостоятельно обходить общий механизм подтверждений.

# 4. Контракт результата операции

Все исполнители должны возвращать унифицированный результат.

Предлагаемая структура:

`ActionExecutionResult`

Поля:
- `operationId`;
- `status`;
- `success`;
- `message`;
- `entityId`;
- `errorCode`;
- `completedAt`;
- `metadata`.

Допустимые итоговые статусы:

- `COMPLETED`;
- `REJECTED`;
- `CANCELLED`;
- `EXPIRED`;
- `FAILED`.

Ожидание подтверждения не считается выполнением.

Успешный результат формируется только после подтверждения фактического выполнения операции.

# 5. Unified Data Layer

Предлагается сохранить функциональное разделение хранилищ, но унифицировать правила их взаимодействия с исполнительной системой.

Основные требования:

- единый контракт чтения и изменения;
- контроль успешности записи;
- обработка ошибок;
- защита от повторных операций;
- согласованное обновление зависимых компонентов;
- возможность последующего перехода на более развитую систему хранения.

Текущие SharedPreferences пока не заменяются автоматически.

Вопрос перехода на Room будет решаться после отдельной оценки требований к целостности данных, объёму информации и транзакциям.

# 6. Unified Data Changes

Предлагается единый механизм публикации изменений.

Структура:

`AppDataChanges`

Области изменений:

- `tasks`;
- `budget`;
- `calendar`;
- `places`;
- `subscriptions`;
- `profile`.

Все заинтересованные ViewModel должны подписываться на необходимые им события.

Особое требование: изменение задачи должно обновлять не только список задач, но и календарь, если задача отображается в календарном представлении.

Уведомление об изменении публикуется после успешного сохранения.

# 7. Unified Reminder Manager

Два независимых планировщика предлагается заменить единым механизмом.

`ReminderManager`

Подсистемы:

- Reminder Registry;
- Alarm Scheduler;
- Reminder Receiver;
- Notification Delivery;
- Boot Recovery.

Основные операции:

- создание напоминания;
- перенос;
- отмена;
- проверка актуальности;
- обработка срабатывания;
- восстановление после перезагрузки;
- защита от повторного уведомления.

Каждое напоминание должно иметь уникальный идентификатор, связанный с исходной задачей или событием.

При срабатывании система проверяет:
- существует ли исходный объект;
- актуально ли время;
- не отменено ли напоминание;
- не завершена ли задача;
- не было ли уже доставлено уведомление.

Старые Alarm не должны приводить к устаревшим уведомлениям.

Точность срабатывания должна настраиваться с учётом возможностей и разрешений Android.

# 8. Обработка ошибок и восстановление

Предусматриваются следующие ситуации:

- отсутствие интернет-соединения;
- недоступность облачной модели;
- ошибка исполнительного модуля;
- ошибка сохранения;
- повторное получение команды;
- прерывание выполнения;
- перезапуск приложения;
- перезагрузка устройства;
- потеря или истечение подтверждения.

Система должна различать:
- операцию, которая не начиналась;
- операцию, которая была подготовлена;
- операцию, выполнение которой началось;
- операцию с неизвестным результатом;
- успешно завершённую операцию.

При неопределённом результате нельзя автоматически повторять потенциально необратимое действие без проверки его фактического состояния.

# 9. Безопасность и контроль операций

Предусматриваются:

- проверка полномочий;
- подтверждение чувствительных операций;
- идентификаторы операций;
- защита от повторного выполнения;
- проверка входных параметров;
- журналирование;
- контроль состояния ожидающих операций;
- защита от обхода исполнительной системы.

Особое внимание уделяется финансовым операциям и удалению данных.

# 10. План перехода на новую архитектуру

Переход предлагается выполнять постепенно.

**Этап 1. Архитектурная основа**

- единые контракты;
- Action Registry;
- единая модель результатов;
- единая модель операций.

**Этап 2. Подтверждения**

- Confirmation Manager;
- устранение двух независимых очередей;
- контроль срока действия;
- отмена и повторное подтверждение.

**Этап 3. Исполнительная система**

- Execution Engine;
- подключение Task Executor;
- подключение Calendar Executor;
- подключение Budget Executor;
- запрет прямых изменений в обход исполнителей.

**Этап 4. Слой данных**

- единый контракт сохранения;
- AppDataChanges;
- синхронизация ViewModel;
- защита от повторных записей.

**Этап 5. Напоминания**

- ReminderManager;
- единый реестр;
- актуализация Alarm;
- восстановление после перезагрузки.

**Этап 6. Интеллектуальный слой**

- единый контракт локальной и облачной моделей;
- передача структурированных намерений;
- сохранение контекста;
- исключение ложных заявлений о выполнении.

**Этап 7. Интеграционные испытания**

- проверка всех модулей;
- проверка подтверждений;
- проверка сбоев;
- проверка восстановления;
- регрессионные испытания.

# 11. Критерии готовности

Архитектура считается реализованной, если:

1. Все изменения данных проходят через единый исполнительный механизм.
2. Ни одна модель ИИ не может самостоятельно объявить операцию выполненной.
3. Подтверждения имеют идентификаторы и контролируемый жизненный цикл.
4. Повторная команда не приводит к случайному дублированию операции.
5. Все зависимые интерфейсы получают необходимые уведомления.
6. Напоминания корректно создаются, переносятся и отменяются.
7. После перезагрузки устройства система восстанавливает необходимые напоминания.
8. Ошибки сохранения не маскируются сообщениями об успехе.
9. Облачный и локальный режимы используют одинаковые правила выполнения действий.
10. Новые функциональные модули могут подключаться без перестройки всей исполнительной системы.

# 12. Открытые вопросы для согласования

До начала реализации необходимо определить:

1. Допускается ли более одной ожидающей операции в диалоговой сессии?
2. Какие операции требуют обязательного подтверждения, а какие могут выполняться сразу?
3. Как долго действует подготовленная операция?
4. Какие операции должны иметь возможность отмены после выполнения?
5. Какой уровень истории операций необходимо хранить?
6. Должен ли исполнительный механизм работать при полностью автономном режиме без интернета?
7. Какие операции должны восстанавливаться после аварийного завершения приложения?

---

**Итоговое назначение архитектуры**

LifeAssistant должен представлять собой единую интеллектуально-исполнительную систему.

Пользователь взаимодействует с одним помощником, который понимает запросы, располагает информацией о функциональных возможностях приложения, может управлять ими, контролирует выполнение и достоверно сообщает о результате.

Внутренние модули остаются специализированными, но подчиняются единым правилам управления, безопасности и исполнения операций.
